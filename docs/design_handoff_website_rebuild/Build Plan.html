Website build plan.

A handoff-oriented spec for systematically rebuilding accelerator-x.io. The goal of this document is a locked sitemap, page-level block outlines for every page, and a small set of decisions to unblock the rest of the work.

It is deliberately not a wireframe. Wireframes are downstream of the structure agreed here. The artefacts that go to engineering are: this doc → component library at hi-fi → clickable walkthrough.

01 · Framing

The handoff lens.

Every artefact in this rebuild is evaluated against one question: does it reduce ambiguity at implementation time? If the answer is no, it doesn't get made.

The work that measurably accelerates a clean implementation in Claude Code is:

  • Locked IA — every page, every URL, every cross-link, no ambiguity.
  • Content structure per page — the blocks in order, what each one does, what real copy lives there.
  • A component library at production fidelity — the reusable pieces (hero, card, CTA band, etc.) with their states and tokens, in the new design system.
  • Interaction specs — what hovers, what animates, what's a modal vs. a route.

The work that looks useful but mostly creates rework downstream:

  • Pixel-perfect mockups of every page before the IA is settled.
  • Design-system polish applied page-by-page instead of to the underlying components.
  • Animations specced in design tools that won't translate to web cleanly.
Design-system question, answered Apply the new design system here, but only to the ~12 reusable components in §08. Pages are composed from those components downstream; mocking every page in the new system is wasted work the developer will redo anyway.

04 · Marketing

Marketing pages — block outlines.

Block-level structure for each marketing page. "Block" = a contiguous section in the page; in implementation this maps roughly 1:1 to a React component. Annotations: existing uses an existing wireframed section; new needs design.

Conversion principle — applies to every page One CTA, one path: "Apply to work with us". No "book a call" buttons. No direct calendar embeds. No "talk it through (20 min)" alternates. Every interested visitor flows through the application form on /contact (or /programmes/[slug]/apply for funnels), which captures the minimum pre-qualification we need. We review every application personally and reply with a booking link only if it's a fit. This rule is non-negotiable across marketing pages, offering pages, and the home — funnels follow it too. Phase 0 specifically is not a cohort — start date is agreed on signing, typical lead time ~3 weeks; the page should communicate "starts soon" without a fake calendar date. Cohort-based programmes (Leadership Cohort, Sr. Leader Acceleration) do have fixed dates and may surface scarcity copy.

  10. FooterGlobal.

TPL · variant Company Enablement — two-phase page /what-we-do/company-enablement

Intent: A visitor lands here from anywhere — nav, ad, peer link, search — and within one screen understands that Phase 0 is where everyone starts, and Phase 1+ is what happens after. The page makes the sequencing impossible to miss; deep-linking to Phase 1+ on its own is not a thing.

  1. Top nav
  2. Detail hero OfferingHeroVariant: shows the two-phase arc visually in the header. "How a company moves with us: Phase 0 → Phase 1+." Sidebar card pushes Phase 0 as the start CTA.
  3. The arc newA simple two-step diagram or labelled sequence: Phase 0 (2 weeks · strategy & activation) → Phase 1+ (8-week cycles · build & ship). Makes the dependency obvious before anyone scrolls.
  4. Phase 0 section PlanLayers + DeliverablesGridFull Phase 0 content: what it is, what you get, who it's for. Section-level CTA: "Book a Phase 0".
  5. Bridge newOne-screen transition: "What Phase 0 produces — and what we do with it next." Visual handoff cue.
  6. Phase 1+ section PlanLayers + DeliverablesGridFull Phase 1+ content: the three streams, what ships, how cycles chain. Section-level CTA is softer: "See if you're ready for Phase 1+" (links to readiness or contact).
  7. Fit check FitCheckFor the full arc, not per-phase. "This is for companies who want to build capability — not just buy a strategy deck."
  8. FAQ FAQListFront-and-centre: "Can we skip Phase 0?" answered honestly. Other questions: pricing structure across phases, how cycles chain, what "+" in Phase 1+ means.
  9. Proof ProofRowFeatured case study that spans both phases. Outcome over time.
  10. Final CTA band CTABandSingle CTA: "Apply to work with us". Routes to /contact. No "book a Phase 0" or call-alt button — every Phase 0 starts with an application. Hero/sidebar shows Duration · 2 weeks · From £5,000 · Typical lead time ~3 weeks · Start date agreed on signing. Not a cohort date.
  11. Footer
Why this is a variant, not a fork The template is the same as other offering pages — same components, same rhythm. What changes is that Phase 0 and Phase 1+ each occupy a full "section pair" (PlanLayers + DeliverablesGrid), with the arc diagram + bridge component making the sequencing obvious. If we ever add a Phase 2, it slots in as another section pair without restructuring.

How a VSL page differs from an offering detail page

Same brand, same design system, but the page does a different job. Compared to /what-we-do/[slug]:

  • No top nav — or a stripped, single-link nav. Removes exit routes.
  • Single CTA, repeated — only one action on the page: apply.
  • Video sales letter at the top — embedded video (3–8 mins) with a fallback transcript. This is the spine of the page.
  • Conversion-engineered copy order — promise · pain · proof · plan · price · objections · CTA. Not the marketing-site order.
  • Scarcity cues — next cohort date, places left. Honest, not fake.
  • Anchor CTAs throughout — every block ends with a button.
Phase B deliverable The full VSL block-by-block spec — what's said in the video, what each section accomplishes, the objection-handling pass, the apply form fields — is the next document I'll write after this one is signed off. Responsive behaviour

Mobile-first, three breakpoints. The component library is where responsiveness is solved — pages compose responsive components, they don't fight CSS. Notes below are the contract Claude Code should build to; mobile-specific mockups will follow for the 2–3 screens where the behaviour isn't obvious from these rules.

Breakpoints

  1. Mobile · < 640pxSingle column. Default state. All copy and CTAs validated at 375px width (iPhone SE).
  2. Tablet · 640–1024pxTwo columns where it helps; otherwise still single. Nav remains drawer until ≥ 1024px.
  3. Desktop · ≥ 1024pxFull layouts as designed. Max content width 1200px; comfortable reading column 680px.

Per-component rules

Nav
Below 1024px: logo + hamburger only. Drawer opens full-height from right, contains the mega-menu items as a stacked accordion. Active page highlighted. CTA pinned at drawer bottom.
Hero / PageHero
Title scales fluidly (clamp), drops one size at mobile. Dual CTAs stack vertically, primary on top, both full-width within content padding. Sidebar info card (offering pages) moves below the hero text.
OfferingTable

Global rules

  • Touch targets ≥ 44 × 44px. All CTAs, nav items, accordion handles, form controls.
  • Body font 16px minimum at mobile. No 13/14px body copy — it triggers iOS zoom-on-focus on inputs and is unreadable in sunlight.
  • Side padding 20px at mobile, 32px at tablet, 48px+ at desktop. Never edge-to-edge text.
  • Fluid type via clamp(). Display sizes scale between mobile and desktop — defined in tokens.css, not per-component.
  • No horizontal scroll, ever. Includes tables (see OfferingTable), code blocks (wrap), and image overflows.
  • Sticky CTA on funnel pages only. Marketing pages don't get a sticky apply bar; VSL pages do, appearing after scroll past the hero, dismissable.
  • Animations honour prefers-reduced-motion. Default to subtle; disable transforms when the user has opted out.
What gets mocked, what doesn't Most components above are deterministic from the rules — Claude Code can build them without a mobile mockup. The two screens worth designing explicitly at 375px are: (1) Home (vertical rhythm of so many sections needs a sanity check) and (2) Offering detail · Company Enablement (the two-phase arc + bridge + section pairs are the densest layout in the system, and the most likely to feel cramped). A third optional one: VSL lander, if the video + sticky-CTA + scarcity-card stack needs validation before build.

Analytics & instrumentation.

Why PostHog

10 · Content pipeline

Content pipeline.

Markdown in repo + a Claude-powered authoring loop. The goal: make publishing fast enough that we can radically dial up the cadence — without sacrificing voice or quality. Insights, case studies, and events all run through the same pipeline.

The data model

All content lives in /content/ as Markdown with YAML frontmatter. One file = one piece of content. Tiles, indexes, RSS, and SEO metadata derive from the frontmatter at build time. No CMS to provision or pay for.

The format field on insights is the key one — the tile component reads it and renders differently (play button for podcast/video, read-time chip for articles). Resolves the "podcasts as article types" awkwardness on the current site.

The authoring loop

Three Claude skills, each a different stage of the pipeline. All run via Claude Code, against the repo, producing PRs that you review.

1 · Ideation skill
Pulls from a backlog file + recent analytics signals + topical inputs. Output: 3–5 concrete article ideas with angles, hooks, and target audience. You pick one.
Trigger: weekly, or on-demand
2 · Draft skill
Given a picked idea + voice guide + reference articles + any source material (Loom, transcript, notes), produces a draft Markdown file in /content/insights/_drafts/. Includes suggested tags, hero direction, and a short editorial brief.
Trigger: per idea
3 · Polish & publish skill
Takes a reviewed draft, runs a final voice/clarity pass, generates social post variants, alt text, OG-image hint, and opens a PR. Merge = published.
Trigger: on "ready" tag

Adjacent skills (same pipeline, different output)

Podcast show-notes skill
Given a podcast audio + transcript: produces show notes, chapter markers, pull quotes, social cards. Outputs a Markdown file ready for review.
Case study skill
Given engagement notes + outcomes: produces a draft case study respecting the client-approval constraint. Public-only at launch.
Repurposing skill
Article → thread → LinkedIn post → newsletter blurb. One source, four outputs, each tuned for the medium.

Voice guide — the missing artefact

None of the skills above produce on-brand work without a voice guide: a single Markdown file in the repo that captures how you write. Tone, sentence cadence, no-go phrases, examples-vs.-counter-examples. Without it, AI-assisted writing slides toward the LinkedIn-thoughtleader mean. This is a small write-up I'd recommend doing before the draft skill goes live — 90 minutes of work, multiplies the value of everything downstream.
